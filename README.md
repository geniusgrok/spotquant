# Spotquant

个人研究用的 Binance BTCUSDT 现货交易程序。当前策略为单仓 SMA40。日线影子账面按两根已完成收盘、252 日过滤、新鲜穿越和修复规则产生信号，在真实到达的下一日开盘单次换仓，入场价格用该开盘价；未完成日线的高、低、收盘不参与信号。账户只在会话跟随它。会话看到第一根重新站上均线的收盘就可以先买。趋势仓在会话价格回到均线 0.5% 以内时卖出；该卖单保留 touch 再入许可，影子账面仍持有且出现更新的已完成日线后，后续会话才可买回。普通退出、原生止损，以及影子账面因 4% 不利收盘退出，都会消费旧信号，需要新的入场信号。影子尚未加入时，提前入场仍可持有。修复仓身份从入场保留到实际持仓，交接前免于均线、过度伸展和 4% 不利收盘退出，保护穿价仍优先。保护目标为成交后已验证观察高点回撤 28%。拥挤度只影响新的买入。只做多或持有 USDT，不借币、不做空、不使用杠杆。默认只读，手动启动有限会话，没有后台守护进程；仅依赖 Python 3.13 标准库。

普通新入场（包括提前入场）若已完成收盘高于均线至少 60%，先保持空仓，避免买入后立即按同一过度伸展条件卖出。普通空仓若影子账面已持有、已完成收盘仍高于均线且未过度伸展，而当前会话价格已在均线 0.5% 的卖出区域，也先保持空仓；价格离开该区域后才可买入。影子账面尚未加入的提前入场不受这项 touch 限制，修复仓继续沿用既有的均线和过度伸展规则。拒绝这些买入可减少立即买卖的费用，也可能延后或错过回升。实际卖出的已完成日线仍被锁住，价格回升不会解除它。已准备的 touch 卖出若在撤止损或成交时继续下跌，任一实际卖出成交达到同仓保护价，就消费旧信号；后续部分成交回升也不能恢复再入许可。

会话先卖后买会多付一次费用，换的是在收盘跌破均线之前离开已经回到均线的趋势。4% 不利收盘退出等到下一会话执行，实际损失可能超过 4%；原生保护距离为 28%，停机期间保留最后确认的保护价。本版完整回测结果与复现原件见下节及 GitHub Release 附件。

## 配置与只读运行

在仓库目录内使用 Python 3.13，无需安装第三方包。

```sh
cp config.example.json config.json
python3 -m spotquant status --config config.json
python3 -m spotquant run --config config.json
python3 -m spotquant snapshot --config config.json --out /tmp/spotquant-snapshot.json
```

先填写 `config.json` 的 `account_uid`，使用核验一致的 Binance UID；`state_dir` 使用该账户固定目录。配置不存凭据。

| 字段 | 用法 |
|---|---|
| `environment` | `live`（默认）或 `demo`，账户、凭据和状态分别隔离 |
| `session_seconds` | 会话时长 1～86400 秒，默认 300 |
| `poll_seconds` | 轮询间隔 1～60 秒，默认 5，不超过会话时长 |
| `capital_limit_usdt` | 可选正值十进制字符串，按当前全账户 BTC 名义约束新增买入；不因持仓升值主动减仓，不是亏损上限 |

主网凭据从 `SPOTQUANT_BINANCE_KEY`、`SPOTQUANT_BINANCE_SECRET` 读取，Demo 从 `SPOTQUANT_BINANCE_DEMO_KEY`、`SPOTQUANT_BINANCE_DEMO_SECRET` 读取。两套凭据互不回退。

`status` 观察一次；`run` 在期限内读取行情、账户和订单状态，输出策略与订单预览。`snapshot` 导出新鲜只读账户 JSON，输出文件必须不存在。`run --execute` 没有 `--authorize-uid` 时仍在读取配置前拒绝。

有资金上限的主网写入口（默认关闭）：

```sh
python3 -m spotquant run --config config.json --execute --authorize-uid <LIVE_UID>
```

配置必须是 `environment=live`，并带正的 `capital_limit_usdt`；`--authorize-uid` 必须与 `account_uid` 一致。资金上限含义见上表。Demo 使用下面的 `demo-check`，不共用主网凭据或状态目录。

## Demo 会话

```sh
cp config.demo.example.json demo.json
python3 -m spotquant demo-check --config demo.json
python3 -m spotquant demo-check --config demo.json --execute --authorize-uid <DEMO_UID>
```

填写专用 Demo UID、固定状态目录和正值资金上限。执行需显式 `--execute`，且 `--authorize-uid` 与配置一致。冷启动等待新鲜穿越，不强造入场；SELL 优先于新 BUY，不预支预计卖出所得。

## 执行与保护（Demo / 主网共用）

发送前保存客户端订单身份和分配信息；接受回包后先保存交易所 `orderId`，再查询确认，实际成交按回读归属。回读的身份、方向、参数和累计成交量必须一致，原生订单 ID 不能被另一意图认领，累计成交量不能倒退。成交均价按毛数量累计，持仓数量保留扣费后的余额。同一 BUY 后续较高价成交同步提高持仓及修复高点。已接受止损的价格下限绑定其实际持仓，不能带到后来新买的仓位。未知委托、成交或余额变化阻止新增风险。查询返回 `-2013` 或未完成订单中没有该身份，均不能证明先前发送失败；交易所查询有异步延迟，同一客户端身份在前一张单成交后可以再次被接受。只有传输前的 `NotSent` 证据才允许原身份继续发送；超时、内部错误和重复身份拒绝仍查原单。

卖出或止损第一次缺席只记录观察时间。至少 1 秒后的另一次查询仍缺席，未完成订单中没有原客户端身份、撤单身份或已知 `orderId`，没有该单的已记录成交，且余额仍与实际成交一致，才记录本地 `ABSENT` 并用新身份补一张当前持仓保护。可见订单、查询错误或资金核对失败会重置首次观察；未知 BUY 不走这条路径。`ABSENT` 是受限恢复记录，不是交易所取消或过期的证明。后继也缺席时停止加挂、保留未知并要求核对；跨日、改变保护价或恢复已准备的目标不能重置这项限制。

缺席原身份继续被逐轮查询，仍未确认时禁止新 BUY。原单后来出现在挂单或终态查询中时，先收回身份，核对迟到成交并处理它的后继保护。撤后继前保存恢复进度，中断后继续核验，不能把撤单请求已发出当成完成。原单已重新成为唯一核对一致的保护、或已核实其终态且解除后继冲突后，才退出缺席恢复；同一原身份不能反复取得补单配额。

明确拒绝或已确认终止且零成交的卖出不原样重发，改为重新挂止损；价格已经穿价时，该失败意图最多使用一个同量后继身份补充卖出。若后继也失败，保留真实失败状态，不循环重发同量订单；部分成交后的减量仍按实际剩余数量独立核对。不足最小名义额、交易所不接受的整笔剩余记为残量，不因此永久挡住以后重新达到门槛的卖出或保护。成交观察中断严格超过 80 天时，用本地最后一笔成交编号继续向后核对，并维持原账户资金锚点；没有可续编号仍拒绝。重复编号内容变化、非法成交编号、早于续页边界的成交或余额不符都不能推进为成功。成交方向、累计毛数量与可用的累计成交金额还必须符合原生订单回读，不能只凭余额碰巧一致就认定完整对账。

可卖数量全部被核验一致的原生止损覆盖、只剩不足一步的尾数时，不报人工接管。整笔剩余确实低于交易所门槛时单独报告 `residual_btc`。若整笔持仓可以交易，不能仅因未覆盖部分单独低于最小名义额就把它当成安全残量；可以通过更换整张止损恢复覆盖。外部或参数不一致的挂单不计入确认保护；已经触发而仅部分成交的止损属于未决执行，也不视作仍在等待触发的保护。

已确认原生止损在零成交时到达 EXPIRED、EXPIRED_IN_MATCH 或 REJECTED 终态后，按当前真实持仓重新判断保护，并沿持久后继身份恢复；不重发旧单，也不把查无此单当成这些终态。

同一持仓和数量仍有效、且未触发退出时，每次保护替换使用固定目标。提交前报价的新高仍保存为实际峰值，但先提交并回读确认本次目标，下一轮轮询再更新更高目标。首次 BUY 成交到原生止损回读确认之间，以及现货止损先撤旧单再挂新单时，都存在保护空窗。STOP_LOSS 触发后按市价执行，成交价可能低于触发价；28% 不是最大亏损或组合回撤保证。会话到期或收到停止请求后，不会仅为抬高目标而撤掉已有同仓、同数量的保护。

Demo 和主网 BUY 前均读取当前手续费和交易所最小额，按最新成交价估算扣费及数量取整后的可保护数量。启用第三资产手续费折扣、费率接口不可用，或历史第三资产费用尚未估值时拒绝新增 BUY；程序不更改交易所设置，已有持仓的止损与减仓仍可继续。第三资产成交费会保留原资产数量并标记财务估值未完成；BTC/USDT 余额及订单归属仍须核对。标准、特殊和税费三类佣金按接口分别相加，不能擅自省掉一类。

已有持仓的退出与保护决策不等待拥挤度公共输入；这些输入只约束新的 BUY。公共输入收取时间与会话决策使用同一交易所校正时钟；发送 BUY 前再次核验日线与公共输入是否仍新鲜，跨 UTC 日或收取记录过期时先重新观察。签名完成后、实际发送前仍检查 BUY 截止和停止请求。止损穿价判断使用新取的最新成交价，均价只用于名义金额过滤。明确拒绝的止损会尝试市价减仓；网络超时或交易所内部错误仍按未知订单原身份查询。

收到 HTTP 418/429 后遵守 `Retry-After`，按服务主机把退避截止持久保存到固定状态目录。重新启动，以及 `status`、`snapshot` 入口，都先取得状态锁并恢复退避；等待结束前不向受限主机发请求。拥挤度的公共请求共享相应主机退避，不能通过换接口或缓存到期绕过；主网公共现货限流也阻止同主机账户请求。退避结束仍在会话时限内就继续；超过交易截止但仍在其后 30 秒内时，只做保护收尾，不新增 BUY。退避长于整段收尾时不发送，无法确认保护则报告人工接管。每次刷新交易规则时替换当前约束，不沿用已从响应移除的旧限制。

会话到期、请求停止或首次 Ctrl-C 后停止新增 BUY。收尾截止固定为原交易截止后 30 秒，提前停止时缩短到首次观察到停止后 30 秒；进入收尾较早或较晚都不重新起算。轮询等待和退避等待至多每秒检查一次停止。收尾沿原身份有间隔地查询与核对；已经成交但尚未折入持仓的 BUY 也在范围内，包括正常到期时已无 pending 意图、但最后观察失败或风险尚未恢复的情形。再次中断、强制杀进程、断电或交易所不可用可能阻止收尾，无法确认的风险保留为未知并报告人工接管。进程退出不代表所有仓位已平仓；已确认的原生止损继续留在交易所。

入场当日的最低价不作为已经穿价的证据；当日收盘仍可用于判断。会话内持仓峰值来自实际成交及成交后运行时观察到的已验证报价，不使用成交前的未完成日线高点。轮询观察不等于完整 tick 最高价。下次会话只按新报价更新保护，原生回读确认后才生效；不能追认停机期间持续移动止损。Demo 回读和只读快照不代表主网执行已验证。

固定状态目录的 `latest.json` 保存最新报告。成功观察包含 `risk_state`（余额、已确认止损覆盖、未保护数量、订单核验完整性、第三资产费用估值及观察时间）、`execution_evidence`（报价、成交/止损回读、费用及滑点）；`status` 和 `run` 也记录 `runtime_identity`。会话启动元数据使用本地 UTC 时钟并标记 `session_started_clock=local_utc`，不为填写报告绕过退避去请求交易所时间；交易决策仍使用交易所校正时钟。市价单的成交滑点以生成意图时的账户复核报价为参考，包含提交前变价，不能视为纯延迟滑点。可选环境变量 `SPOTQUANT_SOURCE_SHA` 记录操作者提供的部署提交，未设置时为空。预算或拥挤度阻止入场后，预览汇总和子项都报告最终动作及原因。

执行会话中报告文件写入失败会停止新增 BUY，并沿既有时限尝试保护收尾。最终报告仍无法保存时返回 `status=unknown` 和 `report_persistence_failed=true`；报告故障不会跳过本可恢复的保护，订单意图的数据库持久化仍是发送前置条件。

停止后的快照并非实时账户状态。`manual_takeover` 为真表示仍需核对可卖持仓保护、未知风险、未决或外部订单，或未完成的状态接管；只剩不可卖残量时看 `residual_btc`。受限缺席恢复已挂好后继保护时，可以没有未保护的可卖 BTC，但 `order_confirmation_complete` 仍为假，`awaiting_original_client_ids` 列出继续查询且阻止新 BUY 的原身份。`recall_pending_client_ids` 表示原单已复现而后继冲突尚未解除，此时仍须人工核对。`account_reconciled` 说明是否完成执行账户核对；资金或持仓无法对应时，即使观察到足额止损仍报告未知和人工核对。保护数量不能代替订单终态或账户资金核验；不要公开提交账户报告。

## 账户状态

固定 `state_dir` 保存 `intents.sqlite`、成交归属、有限观察记录、`latest.json` 和执行锁。同一账户只使用一台机器、一个客户端，Demo 与主网不共用目录。使用独立 BTC/USDT 现货账户；手工订单、已有 BTC、转账和其它资产不会自动认领为程序持仓。账户余额、资金变化或订单归属无法核对时停止新增风险，保留状态并人工核对，不删除数据库或换空目录绕过。当前模型保存已处理开盘时间和已消费信号，重启不会重复换仓或借旧影子信号再入。已有持仓不补仓。残币保留归属并计入持仓和风险，达到数量步长的残币保守阻止新增 BUY。

当前状态规则为 `2026-10-09-absent-order-closeout-v3`。参数完全相同的单 SMA40 v7 已知旧规则可以在相应环境、有资金上限且显式授权的执行会话中升级。程序先校验检查点、持仓、原委托身份、账户余额和属于程序的实际成交。`2026-10-09-spot-safety-recovery-v2` 和 `2026-10-09-verified-realtime-peak-v1` 保留已经验证的会话峰值；更早、尚未验证峰值来源的兼容版本，仍从有证据的 BUY 成交及新报价重建。已确认的原生止损下限继续绑定原持仓，旧的未发送 BUY 作废。全部核对成功后才保存当前规则并继续运行。旧代码会拒绝升级后的状态，防止重新启用已修复的未知单重发与错误再入路径；不要切回旧代码或手工改规则字段接管。

只读 `status` / `run` 遇到待升级规则仍报告 `blocked`，不能替代执行对账或自动取得执行授权。主网也必须经过本节前述的 UID 和资金上限入口；不满足时保留现有原生保护并人工核对。不要改 `environment`、UID 或数据库把主网状态转成 Demo。

v5、v6、旧三仓、不同参数、未知规则或缺失归属证据的状态拒绝接管。尚未升级的旧库可用写入它的确切旧提交隔离核对：先停止其它程序并备份原状态目录，将下面 `OLD_DEPLOYED_SHA` 替换为该提交，原配置使用绝对路径，且 `state_dir` 仍指向原固定目录；不要创建空库或手工改写旧库。旧版 `status` 也会保存观察记录。

```sh
git worktree add --detach ../spotquant-closeout OLD_DEPLOYED_SHA
cd ../spotquant-closeout
python3 -m spotquant status --config /absolute/path/original-config.json
```

这只恢复旧版本的观察能力，`status` 成功不等于已经平仓。真正的主网收尾需在交易所人工核对并结清 BTC 和剩余委托；结清完成前保留已确认保护。确认无持仓、无未决单后保留原库记录，再处理当前版本的初始化。旧提交不明确或旧库已升级时，不运行旧版本接管，直接保留文件和保护并人工核对。

检查使用离线输入，不连接账户。`blocked` 表示当前权限或配置不允许操作；`unknown` 表示无法确认数据、订单或账户状态，不能当作已成交。先核对 UID、环境、固定状态目录、凭据变量及报告原因；状态不兼容或余额/订单归属不一致时保留原文件，人工核对，不清空重试。
